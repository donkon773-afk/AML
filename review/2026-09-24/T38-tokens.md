# T38 — доска как STATE/DELTA профиля s:2: трафик и экономия (24.09.2026)

Источник: живая лента `agent_sync serve` → `.agent-sync/frames/board.aml` (публикация раз в минуту, только при изменении доски),
счётчики — `.agent-sync/frames/board_state.json`. Каждый фрейм перед записью: `AMLCodec.encode` без потерь → `validate_frame` →
(в тестах) непрерывный `Receiver` с согласованным `s:2`. Сравнение — с JSON-кодировкой NAM того же сообщения.

\* Токены учтены не для всех фреймов: до 06:40 сервер работал на системном Python без `tiktoken` (считались только байты);

**Главный выигрыш — дельты, а не компактность строки:** одно изменение статуса задачи — DELTA в пару сотен байт вместо
полного снимка в 1229 байт; неизменная доска фреймов не порождает вовсе.

## Задержка приёмника шины (§5 сценария)

Шина AML: 60/60 фреймов обработано, опрос 0.5 с
p50 0.314 с, p95 0.513 с, max 0.566 с (порог §5: p95 ≤ 2 с — выполнен)

Замер: `scripts/bench_bus.py` — реальный цикл `aml_bus.receive` на копии `.agent-sync`, 60 фреймов от трёх отправителей
в случайные моменты. Порог p95 ≤ 2 с выполнен с пятикратным запасом.

## Ограничения

- Потребитель, подключившийся посреди ленты, получает RESYNC на первую DELTA (тест) — нужен запрос KEYFRAME; полный STATE
  приходит раз в 30 публикаций. Автоматический `QUERY ?KEYFRAME` — следующий шаг, не сделан.
- Лента `board.aml` не ротируется (≈270 байт/фрейм; за сутки единицы мегабайт) — ротация при
  выпуске в эксплуатацию.
- Аутентификация по-прежнему по файлу на одном ПК (см. CLUSTER_GUIDE §8).
