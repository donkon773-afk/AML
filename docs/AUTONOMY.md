## 2. Рабочий цикл агента

```
1. PY scripts/agent_sync.py next <имя>            # что делать сейчас (≤5 строк)
2. если «почта» → brief <имя>, прочитать, ack <имя>
3. сделать ОДИН атомарный шаг первого пункта
4. проверка: PY verify.py (и тесты своей задачи) — зелёные
5. git add <новые свои файлы> && git commit -m "T<N>: ..." -- <все свои пути>   # одной командой, см. §6
6. PY scripts/agent_sync.py set T<N> status=... "notes+=..." --by <имя>
7. PY scripts/agent_sync.py heartbeat <имя> --limit <%> --task T<N>
8. дел нет → PY scripts/agent_sync.py next <имя> --wait 900
   (блокирует до 15 мин без затрат токенов; exit 0 — появилось дело, 3 — нет)
   → снова п.1. Не завершать сессию, пока есть лимит.
```

Порядок дел в `next`: стоп-линия → критика чужих задач → приёмка (claude) →
почта → свои задачи в работе → свои задачи из очереди (зависимости готовы).
Одна задача в `in_progress` на агента.

## 6. Совместная работа в одном рабочем дереве

Все три агента работают в одной папке и одном git — **и в одном индексе**: `git add` одного
агента попадает в следующий `git commit` другого (24.09 так в коммит доски claude d2e1202 попала
работа antigravity по T14). Поэтому коммитить только так: `git commit -m "..." -- <пути>` — git
берёт ровно эти пути и не трогает чужое в индексе. Новые файлы git по `-- <путь>` не видит, поэтому
`git add <новые> && git commit -m "..." -- <все пути>` — одной командой, без паузы между ними. Поэтому же: править только
файлы своей задачи; перед коммитом `git status` и `git diff --stat` — чужое
не добавлять; не запускать форматтеры по всему репо; при конфликте правок
одного файла — письмо владельцу, не перезаписывать.

## 8. Шкала готовности

Готовность = сумма `вес × доля` по задачам с весом / сумма весов. Доля по
статусу: очередь 0, в работе 0,3, критика 0,7, приёмка 0,9, готово 1. Вехи
и веса — в `board.json` (`milestones`, `milestone`, `weight`); меняет только
куратор, с записью в log.md. Цель ночи — вехи M5 (живые фреймы), M6
(транспорт) и M7 (выпуск r2).
