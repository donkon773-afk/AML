# AML Cluster-Agent Exchange Scenario (T17, draft)

Author: `claude` (curator), 2026-09-24. Critic: `codex`. The scope decision belongs to the user. The frames below were generated by `scripts/cluster_examples.py` and checked against the Lark grammar, NAM schema, and `Receiver.accept`; see the corresponding run log in the historical review archive.

## 1. Participants and roles

| Participant | Type | Role in the exchange |
|---|---|---|
| `claude` | Cloud agent | Curator: assigns tasks, accepts work (`RES *ACC`), asks questions (`QUERY`) |
| `codex` | Cloud agent | Critic: verdicts (`RES *ACC/*REJ`) and findings (`HANDOFF st:BLOCKED` with `CHK:…:FAIL`) |
| `antigravity` | Cloud agent | Implementer: submits work (`HANDOFF st:COMPLETE`) and reports pauses (`ERR BUSY`) |
| `gptoss` | Local model (LM Studio) | Advisory second critic; may send only `RES` and `QUERY`, not a final decision |
| `agent_sync` | Program (dashboard service) | Sole always-on receiver/router and source of board STATE/DELTA frames |

Other agents/models can be added to the receiver's `PERMISSIONS` and `.agent-sync/agents.json`.

## 2. Message kinds and their sources

Rule from T12, confirmed by counter-probes: **the program writes long frames; agents or models write short decision frames.**

| Cluster event | Frame | Source |
|---|---|---|
| Implementer submits a task | `HANDOFF tsk:T<N> st:COMPLETE` plus `SUM/ART/CHK/NXT` | Agent |
| Critic returns work with findings | `HANDOFF st:BLOCKED` plus `CHK:F<k>:FAIL:"reproduction"` | Agent |
| Critic verdict / curator approval | `RES rel:T<N> *ACC` or `*REJ` (`rs:` gives a reason code) | Agent or model |
| Ask about status or reason | `QUERY ?STATUS:#T<N>` or `?WHY:#T<N>` | Agent or model |
| Refusal, limit pause, replay | `ERR err:BUSY|INVALID|REPLAY|EXPIRED…` | Agent or receiver |
| Board snapshot, agent heartbeat/limits | `STATE` / `DELTA` | **Program only** (`agent_sync`), phase 2 |

Example submission followed by a verdict:

```text
!AML:2|HANDOFF|aml-nam|antigravity→codex|1|1790200000000|60000|tsk:T13|st:COMPLETE
SUM:"F4: reset grammar cache in setUp + addCleanup; added isolation test"
ART:tests/test_regressions.py:<sha256>
CHK:verify.py:PASS:"71/71 + 14/14, exit 0"
NXT:"critic: codex"

!AML:2|RES|aml-nam|codex→claude|2|1790200601000|60000|rel:T13|*REJ:#T13|rs:STALLED
```

## 3. Receiver checks

The receiver pipeline is the same one used for model output by `llm_client.validate_and_accept`:
`validate_frame` (Lark grammar, decode round-trip, NAM schema) → `Receiver.accept(json, authenticated_peer, now_ms)`.

It checks:

- sender matches the independently supplied participant identity (`peer identity mismatch`);
- the participant may send this message kind (`unauthorized kind`); for example, the example permission matrix does not allow `gptoss` to send `HANDOFF`;
- the session is `aml-nam` and the recipient is correct;
- freshness: `sent_ms + ttl_ms` is neither expired nor too far in the future;
- sender sequence is monotonic and message ID is unique (reject replay/out-of-order);
- for `HANDOFF`, artifact paths are relative and contain no `..`; hashes remain sender assertions, and the receiver does not open artifact files or execute `NXT`/`SUM`.

The historical test run reproduced all four rejection classes: permissions, TTL, sender mismatch, and replay.

**Authentication:** on one PC, a participant is a process under the same account; there is no cryptographic authentication. The prototype derives `authenticated_peer` from the sender's outbox filename. A multi-machine cluster needs signed frames (for example, HMAC with a shared secret), which is outside this first prototype.

## 4. First-prototype transport

**Schema constraint:** `ttl_ms ≤ 60,000` (`assets/nam.schema.json`). Cloud agents run in 5–20-minute cycles, so a frame cannot wait in mail for the next agent cycle without expiring. The receiver therefore processes frames continuously:

1. Sender appends a frame to `.agent-sync/frames/outbox-<sender>.aml`.
2. `agent_sync serve` reads new complete frames every 1–2 seconds, runs `validate_frame` and `Receiver.accept` within the TTL, checks board roles, and applies allowed transitions: `HANDOFF COMPLETE` → `review`; critic `RES *REJ` → `in_progress`; critic `RES *ACC` → curator review; curator `RES *ACC` → `done`; `ERR BUSY` → pause agent.
3. Accepted frames become human-readable `log.md` entries and `events.jsonl` rows. Rejected frames produce an `ERR` for the sender and a reason in the log.
4. Agents read their `brief`; they do not need to parse transport frames.

This keeps TTL short to limit stale decisions and replay, while the board provides asynchronous coordination.

### 4.1 Task-role authorization and state transitions

`Receiver.accept` checks only the general participant × message-kind matrix. A frame may change the board **only when its sender currently has the required role for that task**. Roles come from `board.json` (`assignee`, `critic`), not the frame. This check happens after `Receiver.accept` and before the board write. On failure, the board remains unchanged; the sender receives `ERR UNAUTHORIZED` and the log records the reason.

| Frame | Authorized role | Prior task state | Action | Otherwise |
|---|---|---|---|---|
| `HANDOFF st:COMPLETE` | Assignee | `in_progress` | → `review`; add `SUM/CHK/ART` to notes and frame to `history/T<N>.md` | `ERR UNAUTHORIZED` / `ERR INVALID` for wrong state |
| `HANDOFF st:IN_PROGRESS` | Assignee | `backlog` or `in_progress` | → `in_progress`; update agent heartbeat | Error |
| `HANDOFF st:BLOCKED` from implementer | Assignee | `in_progress` | Keep state; add blocked note and notify curator | Error |
| `HANDOFF st:BLOCKED` from critic | Critic | `review` | Add `CHK:…:FAIL` findings to notes/history and notify implementer; paired `RES *REJ` changes status | Error |
| `RES *REJ` (`rel`/ops = T<N>) | Critic | `review` | → `in_progress` | Error |
| `RES *ACC` | Critic | `review` | → `approval` (curator `claude`) | Error |
| `RES *ACC` | `claude` (curator) | `approval` | → `done` | Error |
| `RES *REJ` | `claude` | `approval` | → `in_progress` | Error |
| Any `RES` | `gptoss` | Any | **Never changes the board**; logs an advisory verdict and notifies curator | — |
| `QUERY ?STATUS/?WHY` | Any permitted participant | Any | Reply with a task `brief`; no board change | — |
| `ERR BUSY` | Agent reporting about itself | — | Pause that agent | `ERR UNAUTHORIZED` if about another agent |

The curator may return a task after the critic's `RES *ACC`: `claude` sends `RES *REJ` while the task is in `approval`. `RES` without an existing task or with `ops` not matching `rel` is `ERR INVALID`. The historical `gptoss` example checks receiver acceptance only; its effect on board state is governed by the table above.

## 5. Metrics and pilot thresholds (T14)

| Metric | Pilot-ready threshold | Method |
|---|---|---|
| Model strict frame validity | ≥ 80% | `validate_frame` without text repair, over all requests |
| Receiver acceptance | ≥ 80% of strict frames | `Receiver.accept` with the authorization matrix above |
| Semantic task alignment | ≥ 90% | For a verdict on T<N>, `rel`/`ops` point exactly to T<N>; no nonexistent task is referenced |
| Local-model latency | p95 ≤ 60 s for a frame ≤ 300 bytes | From request to completed text. 60 s is 20% of the shortest 5-minute agent cycle and 5% of a 20-minute cycle. At ~3 tokens/s, a 300-byte frame (~100–150 tokens) from gpt-oss-20b is near the limit; T14 measures the actual value. |
| Receiver latency | p95 ≤ 2 s | From outbox write to `log.md` entry |
| Savings vs JSON | Reference only | Example set: 919 / 1,812 bytes (−50%) |

Cluster T14 includes **HANDOFF, RES, QUERY, ERR** (at least 20 requests per kind using real board tasks). `PROP` remains only for comparison with T12's tactical vocabulary (see below).

## 6. AML/NAM features not needed by the cluster

The tactical `STATE/DELTA/PROP` vocabulary was originally created for Arma 3 and is not applicable to agent coordination: entity kinds `grp/unt/veh/cnt`, roles `INF/REC/MEC/ARM`, coordinates `@x,y`, `%H…A…S…` health/ammo/suppression metrics, callsigns, actions such as `ADV/ATK/FIRE/…`, `roe/support`, reasons such as `CONTACT/LOW_AMMO/PLAYER_ORDER`, and the receiver's “ungrounded position” check.

The cluster reuses the envelope (`session|sender→recipient|seq|sent_ms|ttl_ms`, plus NAM/2 `s:`/`tr:` fields), `Receiver` checks (permissions, TTL, replay, revisions, `RESYNC`), `HANDOFF/RES/QUERY/ERR`, and their grammar/GBNF rules.

## 7. Decisions and current implementation

The user-approved phase-2 cluster vocabulary for STATE/DELTA/PROP is the `s:2` NAM/2 profile. It includes task/agent rows, actions `RSG`, `PAU`, `RSM`, `RTN`, `APV`, and reason codes `LIMIT`, `STALE`, `CRITIC_RETURN`, `DEPENDS`. The tactical vocabulary remains a separate profile. Profile updates use full `+` rows in DELTA; codecs reject mixed profiles, and `Receiver` checks action target types and eligibility. See [Compatibility](COMPATIBILITY.en.md) and the [protocol specification](PROTOCOL_SPEC.en.md) for the current contract.

## 8. Prototype acceptance gate

`agent_sync` provides `send <sender> <kind> …` to build frames through `AMLCodec.encode`; `serve` reads outboxes using the rules above; the dashboard displays the frame stream. A full pilot gate requires one complete implementer → critic → curator cycle using frames, a human-readable log, passing `cluster_examples.py --check` and `verify.py`, and a byte/token comparison against equivalent JSON on real traffic.
